## 1. 검토 근거와 용어

원본 PPTX 52쪽, `references/design-workflow-connector.md`, `references/pptx-guide.md`,  
`references/prompt-guide.md`, `rdb/init/01_schema.sql`, `rdb/init/04_views_rls.sql`부터  
`07_card_fee_usage.sql`까지 확인함. 리야가 PPT와 단계 흐름을, 법원이가 SQL과 권한을 독립 검토함.  
클로니가 실제 DB 카탈로그를 읽기 전용으로 재조회하고 두 검토를 대조함. 사용자가 검토안을 승인하여 v2 작성 단계로 진행함.

- NL2SQL: 자연어 질문을 SQL 조회문으로 바꾸는 방식임.
- 정형쿼리: 미리 작성하고 확인한 SQL을 조건이 맞는 질문에 적용하는 방식임.
- 논리 View: 원본 테이블에서 허용된 내용만 보여 주는 DB 조회 창임.
- 행 수준 보안(RLS): 요청 회원에게 해당하는 행만 읽도록 DB가 거르는 규칙임.
- 최악값: 단계가 허용된 재시도를 모두 쓸 때의 최대 설계 시간임.

## 2. DB에서 확인한 사실

`crc/secrets/.env`의 PostgreSQL 접속값을 사용함. 비밀번호와 업무 데이터 행은 출력하거나 저장하지 않음.  
사용자는 관리 계정 `cardlab` 사용을 재지시함. 해당 계정은 DB에서 `rolsuper`, `rolcreaterole`,  
`rolcreatedb`, `rolbypassrls`가 모두 참임. 사용자 예외 승인에 따라 카탈로그만 읽기 전용으로 조사함.  
12개 View의 `SELECT * ... LIMIT 0` 확인이 모두 성공했고 업무 데이터 행 조회는 0건임.  
이 결과는 `cardlab`의 접근만 증명함. 서비스 계정의 최소 권한과 회원 간 격리는 증명하지 않음.

지정된 `04_views_rls.sql`의 View 8개는 모두 DB에 있음. DB에만 있는 View 4개는 아래 추가 SQL에 정의됨.

| 추가 View | 정의 파일 | 내용 |
| --- | --- | --- |
| `app.merchant_usage` | `05_merchant_usage.sql` | 카드, 월, 가맹점별 승인 사용액 |
| `app.customer_delinquency_history` | `06_history_daily_usage.sql` | 최대 12개 완료월의 연체 이력 |
| `app.customer_daily_usage` | `06_history_daily_usage.sql` | 기준일 포함 최대 90일의 일별 승인 사용액 |
| `app.card_fee_usage_6m` | `07_card_fee_usage.sql` | 카드별 자료상 연회비와 최근 6개월 승인 사용액 |

공개 `app` View 8개와 조립용 `app_internal` View 4개가 확인됨. 공개 View와 사용 전제는 다음과 같음.

| 공개 View | 제공 내용 | 결과 단위 |
| --- | --- | --- |
| `app.customer_profile` | 가입일과 연령대 | 회원 |
| `app.customer_cards` | 발급 카드, 상품과 자료상 연회비 | 카드 |
| `app.monthly_usage` | 기준월 포함 최근 6개월 승인 사용액 | 카드와 월 |
| `app.customer_delinquency` | 기준일 이전 최신 완료월 연체 | 회원과 월 |
| `app.merchant_usage` | 최근 6개월 승인 사용액 | 카드, 월과 가맹점 |
| `app.customer_delinquency_history` | 최대 12개 완료월 연체 | 회원과 월 |
| `app.customer_daily_usage` | 최대 90일 승인 사용액 | 회원과 날짜 |
| `app.card_fee_usage_6m` | 카드별 연회비 안내값과 6개월 승인 사용액 | 카드 |

동일한 읽기 전용 트랜잭션에서 `app.member_id`, `app.base_date`, `app.coverage_start`를  
`set_config(..., true)`로 설정해야 의도한 회원과 기간의 결과가 나옴.  
서비스는 세 값 중 하나라도 없으면 SQL 실행 전에 거부함. DB 자체가 모든 View에서 0행을 보장하지는 않음.  
`member`, `card`, `card_txn`, `delinquency`에 회원별 SELECT RLS 정책이 있음.  
View 소유자는 RLS 적용 역할 `app_reader`임. `cardlab`은 테이블 소유자이자 관리자이므로 이를 우회함.  
`sql_retriever_user`에는 원본 `card_id` 또는 가명 `member_id`가 있는 내부 View 2개의 SELECT도 부여됨.  
따라서 서비스 계정을 쓰더라도 생성 SQL의 `app_internal` 참조 차단이 필수임.  
`04_views_rls.sql`의 서비스 계정 비밀번호 리터럴은 별도 보안 개선 대상으로 기록함.

`app.card_fee_usage_6m.listed_annual_fee`는 상품 자료에 적힌 안내값임. 실제 청구 연회비가 아님.  
상품 시행일이 기준일 뒤일 수 있어 시행일과 함께 보여야 함.  
이 View는 실제 `coverage_start`를 적용하지만 `app.monthly_usage`는 제공 시작월의 월초를 사용함.  
제공 시작일이 월중이면 두 View의 사용액을 같은 기간 값으로 직접 비교하면 안 됨.

### D-03: 시간 예산 제안

현재의 전체 30초, 종료 1초, Groq 15초, 통신 재시도 0회는 기존 사용자 채택값을 유지함.  
아래 내부 단계 상한은 실측치가 아니라 개발자가 검증할 설계 목표임.

| 단계 | 정형 경로 상한 | NL2SQL 경로 상한 | 포함 범위 |
| --- | ---: | ---: | --- |
| S-R1 요청 검증 | 1초 | 1초 | 인증 범위, 입력, 날짜 |
| S-R2 경로 선택과 생성 | 1초 | 16초 | 정형 매칭 또는 Groq 15초와 전후 검사 1초 |
| S-R3 계획 검사 | 1초 | 1초 | 슬롯과 제공 범위 비교 |
| S-R4 SQL 검사 | 2초 | 2초 | 구문 트리와 허용 목록 검사 |
| S-R5 DB 조회 | 8초 | 8초 | 풀 대기, 연결, 설정, 실행, 수신, 정리 |
| S-R6 응답 | 1초 | 1초 | 성공 또는 최소 오류 응답 |
| 경로별 합계 | 14초 | 29초 | 전체 30초 이내, 1초 여유 |

S-R6의 1초가 종료 처리 예약값임. 합계에 중복해 더하지 않음.  
가이드의 남은 시간 식 `30 - 실제 경과 - 종료 1 - 남은 외부 호출 최악값`과 시작 기준 1.5초를 적용함.  
추가로 `남은 실제 시간 ≥ 현재 단계부터 끝까지 남은 경로별 단계 상한의 최댓값`을 검사함.  
두 번째 식에는 아직 호출하지 않은 Groq의 15초와 전후 검사 시간도 포함함.  
가이드의 1.5초 시작 기준식과 경로별 단계 상한식이 모두 통과해야 다음 단계로 진행함.  
예를 들어 S-R5 직전 경과가 27초면 3초만 남으므로 S-R5의 8초와 종료 1초를 확보할 수 없어 중단함.  
DB의 8초에는 풀 대기 1초, 연결 1초, 세션 설정 1초, 실행 3초, 수신 1초, 정리 1초를 제안함.  
실제 서비스에서 지연을 측정하여 목표 달성률이 낮으면 이 배분을 다시 정해야 함.

### D-04: 결과 완전성 제안

기존 SQL의 행 상한은 유지함. 반환 행 수가 `LIMIT`보다 적으면 해당 SQL 결과는 완전함.  
반환 행 수가 `LIMIT`와 같으면 추가 행 여부를 알 수 없으므로 `limit_reached_more_unknown`으로 표시함.  
`has_more=true`라고 단정하거나 잘린 행만 합산해 전체 합계로 표현하지 않음.  
Q-08의 20행, 일반 목록의 200행에도 같은 규칙을 적용함.  
0행은 조회 결과 없음으로 표시함. `app.card_fee_usage_6m`의 승인액 0은 관측 기간 거래 0원,  
6개월 집계 컬럼 NULL은 관측 기간 미성립임. 다른 View와 컬럼의 NULL 의미는 별도 정의함.

### D-05: 권한 경계 제안

이번 `cardlab` 메타데이터 조사는 설계 입력으로만 사용함.  
운영 서비스는 `sql_retriever_user`로 접속하여 원본 거래 테이블 무권한을 확인한 뒤 배포함.  
서로 다른 두 회원의 세션 범위를 바꾸어 결과가 섞이지 않는지도 배포 전 확인함.  
현재 DB의 `sql_retriever_user`가 내부 View 두 개를 읽을 수 있으므로 SQL 구문 트리의  
공개 8개 View 허용 목록을 독립 안전 경계로 유지함.  
역할 생성 SQL에 적힌 비밀번호는 파일에 두지 않도록 분리하고 자격 증명을 교체하는 작업이 필요함.

## 5. 단계와 커넥터의 구체화

S-R2 정형 매칭은 질문에서 `의도`, `기간`, `결과 단위`, `지표`, `상태 필터`를 추출하여  
등록 조건과 모두 같을 때만 Q-ID를 선택함. 일부만 맞거나 복수 Q-ID가 동등하게 맞으면  
추정 선택하지 않고 NL2SQL 경로 또는 명확화 오류로 넘김.  
Q-08은 활성 카드, 카드 단위, 기준월 포함 최대 6개 달, 자료상 연회비와 승인 사용액 및 건수 요청에만 매칭함.  
제공 시작일이나 발급일 때문에 실제 기간이 짧아지면 응답에 그 기간과 축소 이유를 표시함.  
실제 청구액, 혜택 손익, 해지 권고, 월별 추세 요청에는 Q-08을 사용하지 않음.

S-R1은 인증된 회원 ID만 내부 상태에 보관하고 원문 질문에서 개인 식별자를 제거함.  
제거를 확신할 수 없는 입력은 LLM 호출 전에 `PRIVACY_REJECTED`로 거부함.  
식별자 검출 규칙과 원문 폐기 시점은 개발 테스트 사례로 고정해야 함.  
S-R3은 계획의 상태와 사유 코드 조합, View, 기간, 단위, 컬럼이 질문 슬롯과 일치하는지 확인함.  
S-R4는 실제 실행할 단일 SELECT의 구문 트리를 검사하여 공개 View 1개와 허용 컬럼만 통과시킴.  
SQL 문자열의 금지어 검색만으로 통과시키지 않음. 검사한 SQL과 실행한 SQL은 같아야 함.

C-01은 Groq `openai/gpt-oss-120b`에 정제 질문과 공개 View 8개 정의만 보냄.  
`GROQ_API_KEY`, 회원 ID, 카드 원본 ID, DB 결과와 내부 View는 전송하지 않음.  
응답은 JSON Schema와 상태 및 사유 조합을 검사하고 `finish_reason=length`, 빈 내용,  
형식 불일치 시 `INVALID_MODEL_OUTPUT`로 종료함. 실제 Groq 호출 성공과 15초 달성은 미검증임.  
프롬프트와 응답 스키마 및 공개 카탈로그는 같은 버전으로 묶고 PPT에서 경로를 표시함.  
Groq 명세 근거: [API](https://console.groq.com/docs/api-reference),  
[모델](https://console.groq.com/docs/model/openai/gpt-oss-120b),  
[구조화 출력](https://console.groq.com/docs/structured-outputs),  
[요청 한도](https://console.groq.com/docs/rate-limits).

## 6. 개선 PPT와 검증 기준

개선본은 `sql_retriever_설계서_v2.md` 스크립트 작성 후 같은 이름의 PPTX를 생성함.  
원본의 제목 개체 틀과 `내용_단쪽` 레이아웃을 유지하고, 새 View 컬럼과 Q-08,  
권한 조사 한계, 시간 예산의 내부 단계 배분을 수정함.  
View 컬럼과 타입은 `work/db_catalog.json`의 현재 DB 결과와 비교함.  
워크플로우 ID와 단계 ID, 커넥터 ID, 프롬프트 스키마의 버전을 서로 대조함.  
PPT 렌더링으로 모든 슬라이드의 글자 잘림과 표 간격을 확인함.

실행 서비스 코드는 이번 설계 산출물에 없음. 따라서 서비스의 SQL 검증, 회원 격리,
