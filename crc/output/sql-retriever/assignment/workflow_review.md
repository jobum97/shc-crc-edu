# SQL 검색기 과제: 워크플로우 독립 검토 기록

검토자: `[보고서 작성자|쉽게]` 역할을 맡은 AI 에이전트  
검토 범위: 단계 흐름, 반복 구간, 워크플로우 명세, Groq 커넥터, 남은 시간 예산  
검토 성격: AI의 독립 의견임. 사람 팀원의 실제 회의 기록은 아님.  
상태: 설계 제안임. 새 SQL 실행과 Groq 실호출 결과는 이 문서의 검증 범위가 아님.

## 시나리오와 기존 설계 확인

교육용 카드 DB에는 연회비 부담 고객군이 있고, 상담 회원 `M-6001`, `M-6049`가 해당함.  
상담사가 카드별 연회비와 최근 6개월 승인 이용액을 확인하는 상황을 가정함.  
승인 이용액은 혜택 실적이나 청구금액이 아님.  
따라서 이 결과만으로 카드 해지를 권하지 않는 범위로 설계함.  
근거: [DB 설명](../../../rdb/README.md), [기존 설계](../sql_retriever_워크플로우설계서.md).

기존 설계는 S-R1 ~ S-R6 순차 처리, S-R2 고정 쿼리와 NL2SQL 분기, 내부 재시도 0회임.  
Groq 호출 상한 15초, 전체 30초, 종료 처리 1초, 단계 시작 기준 1.5초가 문서에 이미 있음.  
새 정형쿼리 Q-08은 S-R2의 고정 경로에 추가함. 다른 단계의 책임은 유지함.

## 단계 흐름 검토안

| 순서 | 단계 | 연회비 비교 질문의 처리 |  
| --- | --- | --- |  
| 1 | S-R1 요청 검증 | 상담사 권한과 요청 회원 확인, 질문에서 식별자 제거 |  
| 2 | S-R2 경로 선택 | 조건 일치 시 Q-08, 미일치 시 Groq C-01 한 번 호출 |  
| 3 | S-R3 계획 판정 | 카드 단위, 최근 6개월, 연회비와 승인금액 제공 가능 여부 확인 |  
| 4 | S-R4 SQL 검증 | Q-08도 단일 허용 뷰의 읽기 전용 SELECT인지 확인 |  
| 5 | S-R5 DB 조회 | 회원 범위를 세션에 설정하고 결과를 최대 200행 수신 |  
| 6 | S-R6 응답 | 금액 단위, 적용 기간, 데이터 한계와 오류를 쉬운 말로 반환 |

모든 단계에서 오류 또는 시작 예산 부족 시 S-R6으로 이동함.  
정형 경로는 LLM 호출 0회, NL2SQL 경로는 최대 1회임.  
Q-08을 추가해도 새로운 반복 경로나 병렬 경로는 생기지 않음.

## 피드백과 수정 제안

| 번호 | 기존 설계의 확인 사항 | 수정 제안과 이유 |  
| --- | --- | --- |  
| F-01 | `고정 조건 일치`가 모호함 | 의도·기간·단위·지표 명시. 오선택 방지 |  
| F-02 | 공개 뷰가 7개로 표기됨 | 뷰·컬럼·프롬프트 동시 갱신. 불일치 방지 |  
| F-03 | Q-02 연회비와 Q-03 승인액이 분리됨 | 카드 단위 Q-08 뷰 추가. 단일 뷰 정책 유지 |  
| F-04 | 두 금액의 차이 설명 부족 | 혜택·청구액·해지 추론 금지. 과잉 해석 방지 |  
| F-05 | S-R5는 1.5초에 시작 가능 | 시작 문턱임을 명시. 완료 보장 오해 방지 |  
| F-06 | `view`가 기존 목록 기준임 | 새 뷰·컬럼 허용. 모델 출력 거부 방지 |  
| F-07 | `cardlab`은 관리 계정임 | 계정 격리 불가 명시. 뷰 검증 필요 |

Q-08 선택 조건: 의도가 `card_fee_vs_approved_usage`, 기간이 기준월 포함 최근 6개월,  
결과 단위가 카드, 요청 지표가 연회비·승인금액·승인 건수의 부분집합인 경우임.  
할인·적립 혜택, 실제 청구액, 해지 권고, 월별 추세를 요구하면 Q-08과 일치하지 않음.  
이때 S-R2에서 고정 SQL을 억지로 쓰지 않고 C-01로 전달하되, 제공 뷰에 없는 지표는  
S-R3에서 `UNSUPPORTED`로 종료하는 정책이 필요함.

## 반복 구간 명세 제안

| 항목 | 설계값 |  
| --- | --- |  
| 반복 구간 ID | 해당 없음 |  
| 대상 단계 | 해당 없음. S-R2의 두 경로는 분기이며 반복이 아님 |  
| 반복 횟수와 최악값 | 0회, 0초 |  
| Groq·SQL 재시도 | 요청 안에서 각각 0회. SDK 자동 재시도도 0회 |  
| 실패 착지 | S-R6에서 오류 코드와 재질문 가능한 범위를 안내 |  
| 호출자 재요청 | 별도 새 요청으로 처리. 기존 요청을 되돌려 재사용하지 않음 |

조회 실패를 자동 반복하지 않아 대기 시간과 중복 실행 범위를 예측 가능하게 함.  
Groq 응답의 일부 JSON이나 DB의 일부 행은 정상 결과로 반환하지 않음.

## 워크플로우 명세 제안

| 항목 | 설계값 |  
| --- | --- |  
| ID와 이름 | W-1 SQL 검색기 |  
| 트리거 | 상담사의 동기 검색 요청 1건 |  
| 목적 | 요청 회원의 허용된 카드 정보만 조회하여 결과와 범위를 반환 |  
| 경로 | 정형 Q-01 ~ Q-08 또는 Groq NL2SQL 중 하나 |  
| 성공 종료 | SQL 검증과 조회 완료 뒤 S-R6에서 단위·기간·한계를 포함한 응답 |  
| 실패 종료 | 입력·계획·검증·외부 연동·DB·시간 오류를 S-R6에서 표준 코드로 반환 |  
| 전체 예산 | 30초. 요청 수신 직후 단조 시계로 측정 시작 |  
| 외부 호출 최악값 | `max(정형 0초, NL2SQL 15초) + 반복 0초 = 15초` |  
| 내부 처리 몫 | 전체 30초 - 외부 15초 - 종료 1초 = 최대 14초 |  
| 재개 | 별도 상태 저장 없음. 재요청은 새 요청으로 처음부터 처리 |

14초는 내부 처리에 배정한 설계값이며 실측 성능 보장은 아님.  
Q-08은 SQL 하나를 새로 등록하는 변경이므로 워크플로우의 시간 계산 방식은 유지 가능함.

## Groq C-01 커넥터 검토안

| 항목 | 설계값 또는 반영 필요 사항 |  
| --- | --- |  
| 목적 | 고정 조건에 맞지 않는 질문의 단일 뷰 조회 계획과 SELECT 생성 |  
| 제공자·모델 | 기존 설계의 Groq, `openai/gpt-oss-120b` 유지 제안 |  
| 인증 | 서버의 `GROQ_API_KEY`만 사용. 질문이나 응답에 키 노출 금지 |  
| 요청 | 정제 질문, 확정 조건, 기준일, 제공 시작일, 공개 뷰 스키마, SQL 정책만 전송 |  
| 새 뷰 반영 | 공개 뷰가 8개로 확정되면 새 뷰명과 컬럼·카드 단위 제약 추가 |  
| 응답 | 기존 구조화 JSON 1개, `ready`/`unsupported`/`ambiguous`만 허용 |  
| 제한 | 한 번 호출, 최대 15초, 자동 재시도 0회, 출력 SQL은 S-R3와 S-R4 재검증 |  
| 실패 | 시간 초과는 `UPSTREAM_TIMEOUT`, 429는 `UPSTREAM_UNAVAILABLE`로 S-R6 이동 |

`max_completion_tokens=2048`, `temperature=0.1`, `stream=false`는 기존 설계값으로 유지 제안함.  
새 뷰를 모델에 보여 주더라도 원본 회원ID·카드ID·거래 행은 전송하지 않음.  
위 설정과 모델의 실제 계정 가용성은 이 리뷰에서 Groq 실호출로 검증하지 않음.

사용자가 요청한 `cardlab`은 DB 관리 계정이며 원본 테이블 접근 권한이 있음.  
런타임에서도 이 계정을 쓰는 경우 최소 권한·RLS 보장을 주장할 수 없음.  
SQL 허용 뷰 검사와 요청 범위 통제를 별도로 검증할 필요가 있음.

## 남은 시간 예산 정책 검토안

| 기준 항목 | 값 | 판단 이유 |  
| --- | --- | --- |  
| 전체 요청 상한 | 30초 | 기존 설계와 동일한 사용자 대기 목표 |  
| 종료 처리 예약 | 1초 | 성공 또는 최소 오류 응답을 만들고 반환할 몫 |  
| 시작 기준 | 1.5초 | 전체 예산의 5%로, 새 단계 착수 여부를 단순하게 판단 |  
| Groq 최악값 예약 | 호출 전 15초, 후 0초 | 뒤 단계의 시간을 확보함 |  
| 정형 경로 외부 예약 | 0초 | Q-08 포함 고정 SQL은 Groq 호출이 없음 |  
| 절대 종료시각 | 시작 후 30초 | 규칙·DB·전송의 총합 상한 |  
| 내부 작업 중단시각 | 시작 후 29초 | S-R6의 1초 확보 |  
| 시작식 | `30 - 경과초 - 1 - 미실행 외부 호출 최악초 >= 1.5` | 각 단계 직전 재계산 |

예: S-R2 NL2SQL 분기에서 2초가 지났다면 `30 - 2 - 1 - 15 = 12초`이므로 호출 가능.  
S-R5 앞에서 28초가 지났다면 `30 - 28 - 1 = 1초`이므로 새 DB 조회를 시작하지 않음.  
S-R6은 시작 기준을 다시 적용하지 않고, 남겨 둔 1초 안에서 응답을 끝내는 예외 단계임.  
S-R5의 `statement_timeout`은 남은 내부 시간 이하로 설정함.  
연결 대기도 같은 중단시각에 포함함.

## 통합 시 확인할 항목

- Q-08 질문 조건, 출력 컬럼, 금액 단위와 기간을 SQL 뷰 정의와 같은 말로 맞출 것.  
- 새 뷰 이름과 컬럼을 공개 카탈로그, LLM 프롬프트, SQL 허용 목록에 동시에 반영할 것.  
- S-R6에서 연회비·승인금액 비교의 해석 한계와 데이터가 없는 경우를 구별할 것.  
- 사람의 회의·피드백으로 서술하지 않고 AI 역할별 독립 검토와 통합 기록으로 표시할 것.
